# Decisions

- LibRaw 0.22.2 is fetched by CMake from libraw.org with a pinned SHA-256, not a git submodule: the build sandbox cannot reach other GitHub repos. Shared lib `libraw.so`.
- lensfun is NOT in M1. It needs GLib, which has no ready Android build. Revisit in M3: options are building GLib with meson, or reading the lensfun XML database with a small own parser.
- Only arm64-v8a is built (S24 Ultra). Keeps CI fast.
- M1 modules: app, core:native, core:ui, feature:settings. Other modules from the spec are added when first needed, not as empty stubs.
- compileSdk/targetSdk 37 (androidx Compose 1.12 requires compileSdk 37). AGP 9.4.1, Kotlin 2.4.20, Gradle 9.8.0.
- Until signing secrets exist, CI falls back to a debug-signed APK. Debug keys differ per runner, so updates may not install over the top until the real key is set.
- Render engine is C++ (GLES 3.2) behind JNI, not Kotlin GL: the same code runs headless on Mesa llvmpipe, so shaders and golden images are tested in CI (`tools/golden`). The Kotlin side only marshals a flat float array (core/native/.../engine/params.h mirrors core/render/.../RenderParams.kt; a unit test keeps them equal).
- Working space is linear ProPhoto (LibRaw `output_color = 4`, camera white balance, gamma 1). Temperature and tint are applied as multipliers in that space (approximation of a camera space shift). Kelvin shown in the UI is relative to a nominal 5500 K as-shot.
- Edit base: the half-size LibRaw decode (no demosaic, 2x2 binning, about 3000 x 2000) is the first editable image so Edit opens fast; the full decode is fetched when zoomed past it and for export.
- Base tone curve is fitted from three real S5IIX RW2 files and their embedded camera JPEGs (median per level, rms 0.005 in sRGB units over the observable range, shoulder forced to white). Plus an invisible baseline (saturation +10, texture +25, clarity +10, sharpen +45) so an unedited raw looks like the camera JPEG. The three samples are one scene, so highlight behaviour is extrapolated, not measured.
- Analysis layers for local tone (highlights, shadows, texture, clarity, dehaze) are computed once per geometry at 512 px and sampled in image space, so tiled export needs no cross-tile blur.
- Masks live in the frame after orientation, rotation and straightening but before crop (crop never moves a mask). Brush strokes are vectors in the recipe and are rasterised to a 2048 px alpha image; that image is saved as PNG and is what both the screen and the export sample. AI masks are the same kind of image.
- Masks: up to 8 per photo, 6 parts each, 16 bitmap layers. Detail (sharpen, noise) is global only.
- Constrain to image: the picture shown and exported never contains pixels from outside the source. `Geo.fitCrop` (core/render) takes the recipe crop and, when straighten, keystone, manual distortion or the lens profile would expose the source edge, returns the largest rectangle of the same aspect (moved the shortest way towards the frame centre) whose whole border maps at least 0.15 percent inside the source. It is called from `RenderParams.build` (pass `srcW`/`srcH`), so preview, histogram, analysis layers and tiled export all receive the same crop and the shader needs no change. The crop is shrunk, not the picture scaled, so pixel density stays 1:1 and a lens profile that pulls corners in costs a few percent of the frame (like constrain crop in other editors). The stored recipe crop is untouched; `EditorSession.effectiveCrop` and `Geo.constrainGeometry` give the crop actually used. While the Crop tool is open the fit is off, so the whole straightened frame (with its empty corners) is shown for editing. Masks still live in the frame before crop: the crop only chooses which part of that frame is seen, so a changed effective crop never moves a mask (only code that maps view to frame must use the effective crop). The golden harness carries a C++ copy of the solver; `tools/golden/fitcrop.expected` pins both to the same numbers and `run-golden.sh` renders fitted scenes with outside pixels painted magenta and fails if any remain.
- Heal, clone and AI remove write patches into a half float overlay (long edge up to 3072) laid over the raw before adjustments. Patches are also saved as PNG so edits survive restarts.
- AI models are downloaded on first use (not bundled): they are large (up to 430 MB) and GitHub's 100 MB file limit rules out committing them. Official Qualcomm AI Hub / MediaPipe TFLite releases are used unconverted. MobileSAM, LaMa, SegFormer-ADE20K sky, selfie multiclass were each run on a PC against real photos to confirm input and output conventions before being wired in.
- Delegate choice: LiteRT GPU delegate first, CPU (4 threads) fallback, remembered per model. NNAPI and the Qualcomm QNN delegate were not added: QNN needs a separate vendor runtime package, and the GPU delegate already runs on the Adreno.
- AI denoise uses NAFNet only for fine detail: (denoised - original) minus its own low frequencies, scaled by the amount. Direct use of the model output shifted tone and colour on linear data, and DnCNN (grey only) smoothed far too much.
- Lens profiles: the lensfun library needs GLib, so only its XML data (L-mount lenses, CC BY-SA) is shipped and parsed by our own code. Distortion (ptlens/poly3/poly5), lateral chromatic aberration (poly3/linear) and vignetting (pa) are implemented in the shader. Radius normalisation (seventh pass verdict): vignetting uses half the image diagonal and is verified from the shipped data (Lumix S 20-60 at 20 mm f/3.5, k1 -0.8703, k2 0.1721, k3 -0.1558: gain 1 + k1 + k2 + k3 = 0.146 at the corner, about 2.8 stops, plausible; half the short side would give a negative gain at the 3:2 corner and half the long side a negative one too, so only the diagonal is possible). Distortion and chromatic aberration use half the SHORT side (the inscribed circle, the PanoTools/Hugin convention; the ptlens identity d = 1 - a - b - c only makes sense when r = 1 at the short-side edge). The distortion and CA part is rated high but not proven (lensfun sources are unreachable from the sandbox); closing it needs a brick wall shot at 20 mm on the S 20-60 compared with the in-camera corrected JPEG. Vignetting is interpolated over focal length and log aperture between the calibrations (the correction used to jump half way between calibrated focal lengths). Not handled, on purpose: the calibration aspect ratio and crop factor (the shipped XML has no aspect attribute, and the photo record has no body crop factor; an APS-C lens used in crop mode already gives an APS-C sized image, which is what its profile expects).
- AVIF export is not offered: Android has no AVIF encoder API. JPEG, PNG and 16-bit TIFF are.
- Edits, ratings, snapshots, presets are keyed by `name|size|modified`, so they survive re-indexing and a restore from backup on a new install.
- Edit key stays `name|size|modified` (reviewed in the fourth audit pass, not changed). Two weaknesses: byte identical copies in different folders with the same name, size and time share one edit, and a changed modified time orphans the edit. A content fingerprint (first and last 64 KB plus size) would fix both, but it needs a SAF read of every file at index time, a new photo column and migration, and every existing edit, rating, snapshot, mask and heal file would need a legacy key fallback, which brings the collision straight back for old data. It would also change the backup key format, so old backups would stop matching. Risk outweighs benefit for a personal catalogue where the same file copied with its time kept is, to the user, the same picture. Done instead: the key is built in one place (`Photo.keyOf`) so a content key can be added later as a new key with the old one as lookup fallback and a one-off migration, and backups already carry the key verbatim.
- Restore from backup (fourth pass): ratings, flags and labels carry `updatedAt` (Room v4) and use the same newer-wins rule as edits; a backup without times (older format) only fills rows that do not exist. The zip is read with size caps and an allowlist before anything is written, and the database part is one transaction.
- Room: schema JSON is exported to `core/data/schemas` and committed; every version bump needs the new JSON plus a migration, and `MigrationTest` runs the migration SQL against those files on the host. Downgrades have an explicit step (4 to 3) that keeps all rows; there is no destructive fallback except from version 1, which held only the re-scannable photos index.
- Export service type is mediaProcessing on Android 15+ and dataSync before (mediaProcessing does not exist earlier); both have a system time limit, handled in `onTimeout` by putting the running job back to waiting. The queue restarts when the app is next opened.
- Tags: the sandbox git proxy rejects tag pushes, so milestone tags are not pushed.
- Release signing: a committed sideload keystore (not secret; personal app) signs every build so updates install over the top. Actions secrets, if set, take precedence.

## UI: locked specification (docs/UI_SPEC.md)
- The whole interface follows docs/UI_SPEC.md: black canvas, #1C1C1C surfaces, one blue accent (#437EE4), 0 to 6 dp radii, Roboto, short direct motion, no springs.
- Tokens live in core/ui (LrTheme.kt: Lr, LrSpace, LrRadius, LrDim, LrMotion). Material buttons, switches and checkboxes are replaced by drop-in Lr versions (import aliases), so no Material look leaks through.
- Editor shell: black canvas on top; idle state is a floating 66 dp dock; opening a tool turns it into a fixed stack (parameter tray, category rail, compact master rail). The tray takes layout space, so the photo is refitted rather than covered. Tap the photo or Back to return to the dock.
- Crop is its own workspace (status pill, ruler, circular utilities, Aspect | Geometry tray, X / check bar). X restores the crop from when it was opened.
- Tone curve is drawn over the photo; the tray holds Done, channel selectors and the parametric sliders.
- Known gaps against the spec: the canvas refit when a panel opens is a snap (no FLIP animation, because resizing the GL surface every frame is too costly); no tablet or desktop recomposition; no shared-element return to the library thumbnail.
- R8 minification stays off for release (fifth audit pass). The rules are ready in `app/proguard-rules.pro` and `./gradlew assembleRelease -PminifyRelease=true` builds and keeps the JNI class, but R8 mistakes only show at run time (reflection in LiteRT and the GPU delegate, Room, JNI), nothing in the sandbox or CI runs the app, and a minified build would also make the stack traces in the Copy report unreadable without mapping.txt. Turn it on only after a minified build has been run through the Copy report checks on the phone, and attach mapping.txt to the release.
- Actions are pinned to exact release tags, not commit hashes, because the hashes could not be confirmed from the build sandbox and a wrong hash stops every release. Dependabot proposes tag updates.
- The Copy report never contains file paths beyond photo names, addresses or secrets (`ReportText.redact`), and every free text line passes through it. Photo file names do appear in error lines.
- Viewer and editor browse a frozen id list (sixth audit pass): the list on screen when the viewer opens is kept in the view model (`browseIds`, not saved across process death, where the live list is used). Ratings, flags and edits update each photo in place and never add or remove photos from under the user.
- XMP sidecars are written only for photos in a folder the user added (a document tree). Camera roll and imported photos have no tree to write into, so the app says so (once per session) instead of writing nothing silently. Writing next to camera roll files through All files access paths was not done.
- MainActivity handles `orientation|screenSize|...` itself (no recreation) so the editor keeps its undo history and GL engine when the phone rotates; Compose lays out again. Check insets on the phone.
- The thumbnail disk cache is capped at 300 MB (least recently used first) and written atomically. System thumbnails are still cached on disk (needs phone timings before changing).
- Only arm64-v8a is packaged (`ndk.abiFilters` in app), because dependency libraries ship other ABIs the module level filter does not reach.

## Engine decisions, seventh pass (docs/AUDIT.md)
- Look-changing fixes made on purpose, because the old maths was wrong rather than a matter of taste: negative Dehaze (the sign was inverted, it boosted contrast; now the inverse of positive Dehaze, c * t + A * (1 - t) with t = 1 + d / 2 and the same airlight A, so it is strong on dark pictures: -60 on the sample lifts blacks to display 0.84), local contrast measured against a baseline that includes the global exposure inside masks, and the grading tint without its luma (a hue no longer changes brightness; the old hue offset moved mean luma by +47 levels at full strength, now +3). Colour range and luminance range masks compare in the display domain the picker reads (sRGB through the base curve), so a picked colour selects itself. Needs a look on the phone: Dehaze below zero, a mask with Clarity or Texture under a global exposure change, Colour grading with a strong tint.
- Left alone on purpose (they change the look of existing edits and are design calls, not sign errors): HSL band weights that are not a partition of unity (AE-013: orange moves 1.6 times harder than green; the fix makes orange and yellow sliders weaker by up to 39 percent), grading zones using Rec 709 luma on gamma values (AE-030), Dehaze using a blurred per pixel minimum (AE-033), Texture working at 512 px analysis scale (AE-020), colour noise reduction smearing across edges (AE-032), grain differing between preview and export and its fixed seed (AE-048). They should go behind the look version flag together with the colour contract items (raw white level, white balance luminance, base curve refit).
- Not changed, with reasons: mip chain at 1:1 export (AE-025: the local analysis samples the source at about mip level 3.5, so dropping mips would change the local tone of every export); `destroyEngine` waits up to 500 ms for the GL thread (AE-043: GLSurfaceView drops queued events when its thread exits, so the wait is what makes the destroy run); `Geo.fitCrop` cost (AE-046: its result is pinned by tools/golden/fitcrop.expected and a C++ copy, and its cost is not measured); mask layer texture size 1024 (AE-022: 2048 would cost 64 MB per GL context, needs a phone memory check).
- 16 bit TIFF: float32 intermediate and output targets and a float32 base curve (read with texelFetch, so no float filtering extension is needed), quantised once to 16 bit in native code. The source is still half float (11 bit mantissa), so very bright smooth areas carry about 12.5 bits of tonal steps, not the full 16; shadows and mid-tones are finer. sRGB and Display P3 ICC profiles (version 2.4, matrix and sRGB curve, Bradford adapted colorants, generated in code and tested against the published values) are embedded with tag 34675.
- Export of finished pictures (JPEG, HEIC, PNG) decodes at no more than the GPU texture limit and 8192 px on the long edge, the same cap the editor uses, so a 100 MP stitch exports at 8192 px instead of running out of memory.
- LibRaw is built with OpenMP (static libomp from the NDK, symbols not exported, KMP_BLOCKTIME 0 and passive wait set before the library loads). Output is bit identical to the single threaded build on the sample RAW. The thread count is libomp's default (all cores, including the small ones on a big.LITTLE phone); if the phone shows the small cores slowing the demosaic, cap it with OMP_NUM_THREADS in Native.kt. Deflate compressed DNG is enabled (USE_ZLIB, NDK libz); lossy JPEG DNG is not.
- Decode keeps LibRaw's pixel block and converts it to half float in place (the RawImage keeps the LibRaw instance alive; LibRaw tracks that block in its own allocator, so it cannot be taken out of it). Peak memory on the sample: 420 MB to 242 MB (24 MP full), 144 MB to 98 MB (half size).

## Studio S1b decisions (docs/STUDIO_STATUS.md)
- D1: layer pixels are saved as `PixelContainer` (deflated straight RGBA8, lossless by construction), not lossless WebP. Android bitmap codecs premultiply alpha and lose colour under low alpha. This deviates from the spec's S1 text; S2 revisits WebP with libwebp directly and a device test that every alpha level survives.
- D2: a stroke is stamped on the GPU into an R16F coverage buffer, shown live through the compositor, and committed on pointer up by reading the dirty rectangle back and baking it on the CPU copy (`StrokeReference.commitRect`), so what is saved is what was previewed.
- D3: history keeps before and after pixels of a stroke's dirty rectangle (200 MB, 100 entries) and document states for layer operations, in one linear history. Layers that leave the stack (delete, undo of add) keep their pixels in encoded form (256 MB) so undo can bring them back.
- D4: the CPU copy exists for the ACTIVE layer only; others live on disk and in GPU textures. D5: adding a layer is refused above 600 MB of estimated GPU memory. D6: colours are straight 0 to 1 in the document's blend space. D7: strokes are in layer pixels. D8: autosave at stroke end, after layer operations, on pause and Back, at most every 5 s, on its own thread. D9: a stylus is never interrupted by a palm; a second finger cancels a finger stroke.
- Threads: UI (main), one model thread per session (all state, decode, history, commit), the GL thread (every compositor call, through a queue like `EditorSession.post`), one save thread. Nothing touches a file or codec on main or GL.
- The only way into Studio in S1b is a debug-only screen (long press on the Version row in Settings). `:feature:studio` is a `debugImplementation` dependency and the entry lives in `app/src/debug`, so the release APK has neither. `BuildConfig.STUDIO_ENABLED` exists and is false unless `-PstudioEnabled=true`; S1c puts the mode switch behind it.
- A project made by a newer app is refused with a message rather than opened read-only (the store cannot parse it, so it also cannot be written back).

## Studio S1c decisions (docs/STUDIO_STATUS.md)
- The flag: `studioEnabled` is a Gradle property (`-PstudioEnabled=true|false`), default read from the one line file `studio.enabled` at the repository root (committed as `false`). It sets `BuildConfig.STUDIO_ENABLED`, which source set the app compiles (`src/studioOn` or `src/studioOff`, both hold `StudioEntry`) and whether `:feature:studio` is on the app's classpath, in every build type. With it off no Studio class is in the APK: not the feature, not the model, not `StudioNative` (the Kotlin JNI class moved from `:core:native` to `:core:studio-render` for this; the native library still holds the compositor, about 100 KB, because CMake builds it either way). `tools/check-studio-apk.sh` inspects the dex files for both values.
- PM decision: local and default builds keep the flag off, but the CI release build (the publish job) passes `-PstudioEnabled=true`, so the released APK contains Studio with the Develop | Studio switch visible. Publish rules are unchanged (main only, run head guard, checksum). The `studio-flag` job builds and tests both values and proves both directions on the debug APK; the publish job proves "present" on the release APK before it is copied.
- The debug long press entry (Settings, Version row) now follows the flag, not the build type: it exists in debug builds with the flag on (`src/debugStudioOn`: the activity and its manifest entry; `src/debugStudioOff` has an empty manifest). It hosts the Studio home without mode state.
- D3: `studio.db` is a Room database with one table, `exportSchema = true` and `fallbackToDestructiveMigration(dropAllTables = true)`. It only holds what the project directories already say, so a failed open or a schema change just rebuilds it from the scan (the directories win). This is the one place with a destructive fallback; Develop's database keeps its no-wipe rule. Every database call on the home is wrapped, so a damaged `studio.db` never crashes it.
- D5: flatten export renders full-width strips of at most 4 megapixels through the compositor; PNG is written by the streaming `PngWriter` (exact colour under partial alpha, no bitmap); JPEG is one opaque ARGB_8888 bitmap (48 MB at 12 MP) filled strip by strip with `setPixels`, transparent areas become white. D6: a Display P3 document embeds the P3 profile in the PNG (`IccProfiles`) and in the JPEG (the bitmap carries the P3 colour space, the platform encoder embeds it); sRGB documents embed nothing, as Develop does.
- D7: the start guard counts a Studio start before it begins (`ModeState.startMode`, `switchTo`) and `studioReady()` (the home has drawn two frames) resets it; two starts without a reset fall back to Develop once, with a notice. The counter is written with `commit()` on the main thread: a few tiny writes per mode switch, needed so it survives a crash a moment later.
- Leaving Studio disposes `StudioRoot`, which releases the session, the GL view and the compositor (BK-399); `StudioStats` is cleared and `studio_texture_mb` reads 0 in Develop. Each mode keeps its saved UI state while the other is shown.
- New projects follow the spec: blank presets make one empty (transparent) layer, a photo becomes layer "Photo". S1b's white Background layer is gone from the home path (`StudioProjects.newBlank` is no longer used by the app). Back on the Studio home goes to Develop.
- The lint job is no longer `continue-on-error`: all modules report 0 errors (the one error was a literal byte-order mark inside a string in `core/data`, now written as `\uFEFF`).

## Studio S1b fix decisions (docs/STUDIO_STATUS.md)
- Studio blends in gamma encoded display space by default, as Photoshop does. A linear light option is stored per document (`BlendSpace.LINEAR`) and is off. The S3 reference and every S3 golden run in both spaces. (BK-488, PM decision, 6 Oct 2026.)
- A stroke commits per touched 256 px tile with one undo step; the bytes baked equal the old whole box bake. Pen beats palm (a stylus DOWN cancels a finger stroke; fingers wait 600 ms after the pen leaves). The graveyard keeps only layers history can bring back.
- The GL view is created once per canvas screen and is never detached by a rotation; the compositor is destroyed only when the screen is released.
- Autosave on failure (BK-503): retry delays 5, 10, 20, 40, 60 s, stop after 10 failures in a row until an edit, a pause or leaving; one notice per episode; free space checked before writing (autosave: estimate plus 16 MB, new project, duplicate, import and export: estimate plus 200 MB); leaving with a failed save asks first and offers Export.

## Platform and library first impression (W16, W29)
- Predictive back is switched on explicitly (`android:enableOnBackInvokedCallback="true"`); `BackHandler` stays. The manifest rules and the list of every `BackHandler` are guarded by `PlatformRulesTest`, which reads the repository (system property `repo.root`); the back order is in docs/PLATFORM.md. (BK-246, BK-426)
- The library's filter and sort (`libraryFilter`, JSON), column count (`columns`) and top photo (`libraryTop`, written when the app pauses) survive a cold start. The grid scrolls back to the saved photo once per process, unless the viewer is sending it to a photo. The top photo is the first photo at or after the first visible grid row (`GridRows.topPhotoId`). (BK-120)
- The first export asks for notifications once, with the reason shown first; declining never blocks the export (`NotificationRule`). (BK-285)
- The library opens on RAW photos when the phone holds at least one RAW file and the user has made no choice; two chips, "RAW photos" and "All photos", are an explicit choice that is stored (`viewChoice`) and never overridden. The default only applies where the shown source has RAW photos, so a folder of JPEG files is never an empty grid. The RAW view is not a filter the user built (`LibraryFilter.rawOnly` is not counted in `isActive`, is not stored in `libraryFilter`, and "Clear filters" keeps it). A one time "What's new" note says so (`whatsNewSeen`). (BK-498)
- The grid's order is held while a finger is down, it scrolls or photos are selected, and for 1.5 s after the touch ends (`OrderGate`, `HeldOrder`): deleted photos leave at once, new ones wait, the sorted order is applied once. A new source, a new filter or a grid that is not on screen applies at once. Tile data (rating, flag, edited badge) is always the latest. Heading keys are made unique (`GridRow.Head.key`) because a held order can repeat a day. `grid_resort_count` is in the Library block of the Copy report. (BK-497)
- A scan reads the EXIF capture time of the newest 300 new RAW files, four at a time, before inserting them, so the first screenful is already in shooting order; a failure keeps the file time. `scan_exif_ms` records the cost. Not measured on the phone.

## Studio S1d decisions (docs/STUDIO_STATUS.md)
- Studio is the start mode only if used in the last 30 minutes (one constant, `RESUME_WINDOW_MS`); activity is stamped on switching to Studio, opening a project, pause and Close. No time stamp counts as not recent. (BK-504)
- The open project is remembered in `studio_open_project`; Close clears it, a kill or the mode switch leaves it; the home offers "Continue <name>" when the project still exists. (BK-504)
- RAW in Studio until the Develop hand-off exists (W26): say where RAW photos open, tell the user a DNG is rendered by Android, name the cause of any other failure. (BK-505)

## Colour contract, look version 2 (docs/COLOUR.md)
- Every edit carries `lookVersion` in its recipe. A recipe without the key reads as look 1 and nothing is rewritten on upgrade; look 1 must reproduce the output of the build before looks existed (the 19 golden scenes are pinned to `look=1`, and the fixture numbers under look 1 equal main). New edits, unedited photos and Reset use look 2. A look written by a newer build renders with the newest this build knows. (BK-470, BK-438)
- Look 2 decodes with `adjust_maximum_thr = 0` and applies a source gain `wbGain` = max(cam_mul) / min(cam_mul) in the shader, so white balance no longer changes brightness and a clipped neutral is white. Look 1 applies the factor LibRaw's rule would have applied (`v1Scale`). One decode serves both. (AE-001, AE-023)
- Look 2 has its own base curve table (`kBaseCurve2`, `BaseCurve.TABLE2`): the stored curve re-expressed for a neutral at 1.0 with a cubic shoulder from a knee at 0.55. **The knee is provisional** (approved as provisional): it needs a refit with real highlight rich frames and the camera JPEGs (BK-021, a phone task). `kBaseCurve` never changes (a test pins its SHA-256); a later look adds a table of its own. (BK-440)
- "Update look" (More menu, only for look 1 edits) is one undoable history step. Presets, Paste edits and Paste from last never change the target's look. Export uses the recipe's look. Downgrade: an older build ignores the key and renders look 2 edits as look 1. (W22)
- The colour checks run in the golden CI job: `tools/colour/run-colour.sh` (synthetic DNG charts through the real engine against an independent Python model, both looks), `tools/looks/make_base_curve.py check`, and the host tests named in docs/COLOUR.md. What they cannot prove is the colour of a real camera (BK-441).
- The golden harness reads its `key=value` arguments from tables, one per topic (tone, colour, detail, masks, geometry, optics, look, debug) in `tools/golden/golden.cpp`, instead of one else-if chain: a task adds its keys to its own topic's table, or a new table listed in `kTopics` at the place marked NEW TOPIC, so two tasks no longer edit the same lines. A key in two tables stops the harness at start up. Checked with `cmp` on 37 renders (the 19 scenes, the look 2 scenes, every key at least once, the 16 bit path) before and after: identical. (BK-500)

## Engine residue (AE-041, AE-051)
- AE-051: the local analysis (Texture, Clarity, Dehaze weights) is built from the source with the heal and remove overlay laid over it, after the source gain, as `main.frag` does. The analysis cache is invalidated whenever the overlay changes or is switched on or off. This is a bug fix for every look: an edit with a heal patch and Texture or Clarity renders the patch interior without the spurious boost (a flat patch at Texture and Clarity 80 went from 180 to 242, now 180). Edits without a heal patch render byte for byte as before. Cost: the 512 px analysis and its blurs are rebuilt after each heal stroke.
- AE-041: the audit's claim that the shader gets mirrored EXIF orientations wrong did not hold. `tools/golden/orient_check.py` renders an asymmetric picture under all eight orientations (golden key `orient=N`, the pairs of `RenderParams.orientationToRotFlip`) and compares with the definition of each. The real gap was in the decoder, which mapped only LibRaw flips 3, 5 and 6; `exifOrientationFromLibrawFlip` (`orient_map.h`, the inverse of dcraw's `"50132467"` table, round trip tested) now covers all eight. Dormant for Panasonic and Samsung files, which are never mirrored.
- AE-025 stays as decided: the analysis needs the source mips.

## Shader correctness, look 2 (W23, docs/COLOUR.md)
- HSL band partition (AE-013), the fine Texture radius (AE-020) and grading zone luma (AE-030) are look 2 only, selected by `G_LOOK = 31`; look 1 is untouched. No new JNI call, no change to `kParamFloats`.
- The Texture ring taps carry the source gain and the heal overlay like the pixel does (the audit's patch omitted both), so a heal patch is not boosted at look 2 either (flat patch at Texture and Clarity 80: 180 and 180).
- BK-485 (band centres on sRGB hue) is not done: it would be look 3.


## Automatic backups (W06, BK-142, 143, 303; host tested, nothing run on a phone)
- Three places behind one `BackupTarget` interface, strongest first: plain files in `Documents/Rawline/backups` when All files access is on (any reinstall reads them, no folder pick); a folder the person chose with the system picker (persisted permission, survives an uninstall, picked again after a reinstall); MediaStore `Documents/Rawline/backups` as the weakest fallback (on Android 11 and later the app sees only rows it created, and whether a reinstall sees them again cannot be proved offline, so Settings says "may not be found after a reinstall"). The choice is a pure function (`TargetChoice`), tested.
- The zip is format 2: `manifest.json` last, with the size and SHA-256 of every other entry. The writer reads its own file back and verifies it before publishing; a restore refuses a damaged file and says the first problem. A format 1 zip (no manifest, has `version.json`) still restores with "This is an older backup, it cannot be checked". The reader (`BackupReader`) is unchanged and ignores the manifest; restore is still `Catalog.readBackup` (size caps, allowlist, one transaction, newer wins).
- Run order that cannot lose a backup: write `name.part`, verify, publish by rename, only then delete the oldest beyond 7. Names are `rawline-backup-YYYYMMDD-HHmm.zip`; rotation orders by the name and never touches other files. A leftover `.part` (older than a day, or of unknown age) is removed at the start of every run; runs never overlap (one mutex in the process).
- Triggers: daily (a 24 hour periodic job with 4 hours flex, battery not low), about 2 minutes after every 25th change and after the first change ever, and Back up now. A change counter (`backup_changes`, only ever increases, bumped by saved edits, ratings, flags, labels, presets and snapshots) means nothing is backed up when nothing changed (`BackupPolicy`).
- Scheduler: the platform `JobScheduler`, not WorkManager. The task allowed either; WorkManager would add a library (and its transitive dependencies and size) for one daily job and one delayed job. A `JobService` needs no extra library and no permission beyond the service's `BIND_JOB_SERVICE`. Jobs are not persisted across a reboot (that needs RECEIVE_BOOT_COMPLETED), so the daily job is put back a few seconds after every app start; the edits path and Back up now are the reliable ones. PlatformRulesTest now checks every service (not exported, job service bound by the system, a foreground service type has its permission).
- Settings has a Backups section: where it backs up to, "Last backup: today 14:15, 3.2 MB, in Documents/Rawline/backups", the last failure, an automatic switch, Back up now, Restore from a backup (the backups in the place, newest first, plus Choose a file), Save a copy to (the old save as), and Choose backup folder while All files access is off. Choosing a backup copies it to the cache, checks it and shows "This backup has 312 edits, 1,204 ratings, 18 presets, from 4 Oct. Anything changed more recently on this phone is kept. Restore?" before anything is written. The restore list shows the edit count only for plain files (reading a manifest needs random access); other places show it in the question.

## Card import (W15, BK-096, 344, 431; engine host tested, the Android parts compiled and not run)
- Engine in `core/data/ingest` (pure JVM): one file at a time, `<name>.part`, fsync, read the part back and compare its SHA-256 with the one of the bytes that came off the card, rename, give the copy the card file's time (so `Photo.keyOf` of the copy equals the card's and the library sees no duplicate), then the ledger. The card is only read. A kill leaves only `.part` files, deleted at the next run.
- Dedupe: `ImportLedger` (`files/import-ledger.txt`, appended per finished file, name, size and time to the FAT 2 s). Beyond the task file: a copy already in the folder with the same name, size and time counts as imported even when the ledger is gone, and a card file name with a slash, `..` or control characters is refused.
- Resume means running the same card again: finished files are skipped. A half copied file starts again (there is no byte level resume). Cancel is checked between files and every 256 KB; a cancelled file leaves nothing behind, finished files stay. Disk full (up front or part way), a card pulled mid file, a provider that throws: that file fails with its message and the rest go on.
- Speed: the engine times only the card read and write, not the verify re-read from the phone's storage; the class (SLOW under 20 MB/s, OK, FAST from 80) is reported only after 2 s of copying. The Copy report shows the numbers of the last run, never an estimate. The notification says "Slow reader or card, this will take about N minutes" once it has 2 s of data and the rate is slow.
- DNG probe: reads the TIFF directory at the offsets the file names (so a directory at the end of a 50 MB file is found), not only the first 1 MiB. The Copy report has a "DNG files (Compression tag)" section: the compression number and SUPPORTED or PREVIEW_ONLY of the newest 20 DNG files in the library, so Jai's three Expert RAW photos copied to DCIM/Rawline answer the JPEG XL question without a card import. Compression 1, 7 and 8 develop; 52546 (JPEG XL), 9 and 34892 do not (W15 section 3).
- Android: `SafCardSource` (folder picker tree, DCIM only when there is one, hidden folders skipped), `ImportService` (dataSync, progress and Cancel notification, stops at the Android 15 time limit), destination `DCIM/Rawline/<yyyy-MM-dd>/` through plain files, so it needs All files access (the person is told if it is off); the copies are announced to MediaStore and the library's observer rescans. One entry, "Import from a card", in the Add photos menu.
- Not done (W17): the Preview only badge and the editor text for DNG types that cannot be developed (D7), the Settings toggle for remembering imports, the USB attach trigger.

## Studio S2 decisions (W26: masks, selections, tiles on disk, Open in Studio)
- Selection and masks are 8 bit planes stored as sparse tiles (`TileCodec`: a constant tile is 2 bytes, else deflate; an absent tile is zero). The selection is not part of a history state: the saved document gets its `selection` reference at save time (present exactly when the selection is not empty), and selection edits are their own history entries with the changed tiles' before and after bytes.
- Invert and off for a mask are flags (`inverted`, `enabled`), never a rewrite of tiles. Painting on a mask follows the colour you see: black hides, white reveals, and on an inverted mask the grey is flipped. The brush paints toward the foreground grey, the eraser toward the background grey (as the eraser does on a mask in the programs people know). A mask that is off cannot be painted ("Turn the mask on to paint it.").
- The mask scales the resampled alpha (`alpha' = alpha * opacity * m`, spec 2.1), bilinear in the layer's own pixels, not each texel's alpha before the alpha weighted colour blend: colour is never touched by a mask, and a mask of all 255 is byte for byte no mask (a sum of weights within 1e-5 of 1 is taken as 1 in the shader so rounding cannot break that).
- The selection clips a stroke by the selection value under the centre of each layer pixel (nearest canvas pixel). The same arithmetic runs in the shader (live) and on the CPU (commit), so the preview equals the result. No selection, or a selection of nothing, clips nothing.
- The lasso and the ellipse rasterise by scan conversion and runs, tested equal to the per pixel definition, so the CPU path is usable at 12 MP; the spec's GPU stencil lasso is not needed until the 100 MP cap lands.
- Tile writes for a mask are in place (`mask/<layerId>/t_<tx>_<ty>`), tiles first and the JSON after. The alternative (content named tile generations) would make every edit rewrite more and keep old tiles until a later gc; the cost accepted is that a kill during a stroke's tile writes can leave part of that last stroke on disk. Tile files are never torn and the project always opens (tested at every file operation).
- `project.json` is version 2 because a version 1 reader would silently ignore masks and show the wrong picture; a newer file opens read only through `NewerSchemaException`, which is what we want for a v1 app meeting a v2 project.
- Open in Studio makes a new project and flows nothing back. The layer is a rendered pixel layer flagged `origin: develop` (smart objects arrive in S4); the original is copied to `source/<hash12>.<ext>` and the recipe to `recipe.json` after the first save, so a failed first save leaves no half project. The menu item only exists in a build with Studio.
