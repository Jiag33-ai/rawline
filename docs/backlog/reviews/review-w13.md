What I ran on the host (Kotlin 2.4.10 compiler from the Gradle distribution, JUnit 4, the live studio-model and studio-render sources minus the Android-only files StudioGl, PhotoImport and StudioExporter): the worker's 121 model tests and 27 session tests pass; two probes against the live code (a missed hover exit, a slow failing save) reproduce R3 and R6 below; the fixes for R3, R4 (host part), R5 and R6 pass with 164 tests in total. ## 1. Verdict
The tiled commit, the banded readback, the undo entries, the retry schedule and the pre-checks do what the fixes asked, and the model-thread discipline from S1b still holds. Two things are not done properly and both will show up on the phone: the rotation claim (the GL view is "moved without being detached") is probably false, and an export that is running when Jai leaves the app stalls and then fails. Four smaller holes are proven or easy to prove on the host, and the follow-up W32 closes them.

## 2. Findings (ordered by what will hurt Jai first)

### R1 [P1] `movableContentOf` probably does detach the GL view on rotation; the code that follows is correct only by luck
`CanvasScreen` wraps `AndroidView(factory = { glView })` in `movableContentOf` and the comment says the view is "moved between the portrait and landscape layouts without being detached". Compose keeps the composition state of movable content, but an `AndroidView` is a layout node backed by a holder, and moving it removes the node from one parent and inserts it in the other; the holder takes the child view out of its parent group and adds it again. A `View` that is removed and added fires `onDetachedFromWindow` then `onAttachedToWindow`. For a `GLSurfaceView` that stops the GL thread and destroys the EGL context (`preserveEGLContextOnPause` only holds the context while paused, not on detach). So a rotation most likely destroys the context, and the claimed benefit (no re-upload, no new compositor) is not delivered.
What then happens in the code: `viewDetached` does nothing unless `released`, so `glReady` stays true. Any `post` in the gap goes to `view.queueEvent`, which lands on the dead thread's queue and never runs, and its `onDrop` never fires, so a `gpuCall` waits its full timeout (a stroke commit or a thumbnail: seconds). After re-attach `onSurfaceCreated` runs with `handle != 0`, abandons the old handle, builds a new compositor and calls `onContextRestored`, which re-uploads the layers: that path works (it is the context-lost path) but costs the re-upload the comment says is avoided, and on a 12 MP, five layer project that is a visible pause.
A second, harder risk: if Compose inserts the view at the new place before the old holder has removed it, the second `addView` throws "The specified child already has a parent". I believe the order is remove then insert, but I could not prove it without a device.
Proof: two counters in `StudioGlView` (`onAttachedToWindow`, `onDetachedFromWindow`) and the compositor's create count in the Copy report (`studio_gl_attach`, `studio_gl_create`); rotate five times; expected by the code's claim: attach 1, create 1; if create is 6 the claim is false. Also rotate during a stroke and while the layers panel is open.
Fix: (a) cheap and safe whichever way the proof goes: `viewDetached` sets `glReady = false` when not released so jobs queue in `pending` and `onSurfaceCreated` or `markReadyIfValid` runs them; (b) if the counters say the view is detached, drop `movableContentOf` and use one call site: one `Box` that hosts the surface, and change only the panel arrangement (a `BoxWithConstraints` or `LocalConfiguration` switch around the panels, not around the surface). That keeps the view in one place by construction.

### R2 [P1] An export that is running when the app goes to the background stalls, then fails
`ExportSheet` runs the export in `rememberCoroutineScope` on `Dispatchers.IO`, one `renderStrip` call per strip, and each strip is a `gpuCall` with a 60 s timeout. `onPause` calls `glView.onPause`, `gl.paused()` sets `glReady = false`, and every posted job (the strips) waits in `pending` until the app is resumed. A 12 MP PNG export takes tens of seconds, so a phone call, a notification tap or the screen going off in the middle stalls it; after 60 s the strip returns null and the export says "Export failed. The canvas may be too large for the memory that is free." (a misleading message). The partly written file is discarded. If Jai swipes away to share the picture, that is the same case. W13 added the pause rule (correct, a context can be lost while paused) but nothing makes export aware of it.
Proof: phone, 12 MP project, start PNG export, press Home at 30 percent, wait 90 s, return. Expected today: failed message. Host: `FakeGpu` with `paused()` and a strip call, assert `renderStrip` returns null after the timeout (a timing test with a short timeout).
Fix (design decision for the PM, two options): (a) minimum: keep the screen on while an export runs (`FLAG_KEEP_SCREEN_ON` for the sheet's lifetime), per-strip timeout counts only the time the app is resumed, an honest message "Export paused. Come back to the app to finish." plus a Retry that restarts from the beginning; (b) proper: run the strips on the compositor of a separate offscreen EGL context in a foreground service (the Develop export already has a service), which is a larger change and belongs with S9 (BK-410). I recommend (a) now and (b) with S9.

### R3 [P2] A missed pen hover exit leaves finger drawing off for good (proven on the host)
`onHover(near = true)` set `penNearUntil = Long.MAX_VALUE`, cleared only by a hover exit. If the exit is lost (the pen leaves the screen edge, the app is paused with the pen near, Compose drops the Exit during a recomposition) every finger DOWN is ignored from then on until the pen is hovered and removed again. The probe against the live router confirms it: after a hover enter with no exit, a finger DOWN an hour later produces no action.
Fix (tested, in W32): near hover sets `penNearUntil = timeMs + 2 s` and every hover move renews it, so a missed exit lapses by itself; the exit still gives the 600 ms grace. Test: enter, no exit, finger at +3 s starts a stroke; enter, moves, finger at +1 s ignored.

### R4 [P2] Leaving does not wait for the save, so BK-503's dialog only protects a failure that already happened
`tryLeave` asks only if the state already says FAILED or NO_SPACE. `leave()` calls `session.flush()` (returns at once) and goes straight to the thumbnail and `onExit`, which releases the session. If the flush itself is the save that fails (the phone filled up since the last good save: exactly BK-503's case), the failure is reported after the screen has gone, the toast is on a screen that is leaving, and the work is lost silently. The dialog would have caught it only if the failure had happened earlier.
Fix (host part tested in W32): `flushAndWait(timeoutMs)` returns the save state after the flush finished or the time ran out; `leave()` calls it on `Dispatchers.IO` (it sleeps in 20 ms steps, never on the main thread) and if the result is FAILED or NO_SPACE it sets `confirmLeave = true` and stays instead of leaving; DIRTY or SAVING after 5 s counts as unsaved too. The Compose edit is specified, not compiled. Test: failing writes, `flushAndWait(2000)` returns NO_SPACE, and with writes restored a second call returns SAVED.

### R5 [P2] Duplicate on a full or failing disk can leave a half copied project that appears on the home (proven)
`Catalog.duplicate` copies file by file into the new folder and saves. SpaceCheck is checked before, but the check is a guess; if a write fails half way (the check passed with 80 MB free and the project is 90 MB, or the disk fills during the copy) the new folder stays, with a layers directory but maybe no `project.json`, and the scan lists a damaged project or an "Untitled" row. Fix (tested): any failure deletes the new folder and rethrows. Test: the MemFs throws on the third write, the folder does not exist afterwards.

### R6 [P3] The retry gap is counted from the start of the failed save, not from the failure (proven, modest)
`wait = lastSaveStart + spacing - clock` means a save that takes 30 s to fail (a slow flash write on a nearly full phone) gets its 5 s retry gap already used up, so the retry starts at once and the schedule 5, 10, 20, 40, 60 s is not what Jai's phone sees: attempts are spaced by the save duration only. The probe with a save that takes a while to fail shows the second attempt immediately. Effect is modest (the MAX_TRIES stop still comes, but sooner than ten spaced attempts). Fix (tested): `lastFailureAt` set in `onSaveFailed`, used as the base while `saveFailed`.

### R7 [P3] The Compose leave dialog's three buttons share one row; the touch targets are text buttons
"Leave", "Stay" and "Export" are `LrTextButton`s, two of them inside a `Row` in the dismiss slot. On a narrow phone in a large font the row can clip. Not a defect in logic. Proof: font scale 200 percent screenshot. Fix: use the vertical button stack that the other dialogs in feature/studio use, 48 dp targets (BK-403 rule).

### R8 [P3] The graveyard cap can evict a layer that undo still needs, and the toast says "cleared to free memory" at the time of the delete, not at the undo
`stash` evicts oldest first at 256 MB regardless of `restorableLayerIds`. `pruneGraveyard` keeps restorable ones, but the cap does not know about them, so deleting three large layers can silently drop the first one's pixels while its delete is still on the undo stack; the toast appears at the later delete, and the user finds a blank layer when undoing the first. Not a crash (`lost` is checked on restore) and rare. Proof: host test with 300 MB of layers (`FakeGpu`, 3 layers of 10 MP each), delete all three, undo three times: expected today: the first undo returns a blank layer. Fix: evict the oldest only among ids no longer restorable first, and when forced to evict a restorable one say so in the toast ("Undo of deleting Layer 2 will bring back an empty layer").

### R9 [P3] The undo entry for a stroke is tested with fakes only
`History.Entry.Strokes` and `Step.SetPixelsMany` have tests, and the session test uses `FakeGpu`; what is not tested anywhere is the real native tile readback against the Kotlin tile bake on the phone (the Mesa golden covers the shader, not `readStroke` bands). Proof: the S2 golden or an instrumented test: one long diagonal stroke on 4000 x 3000, commit, undo, redo, compare layer bytes to the first commit. Until then the claim "banded readback identical" is the CPU side only.

### R10 [P3] The export space check looks at one volume
`SpaceCheck.problem(context.filesDir.usableSpace, ...)` is right for app files. Pictures and a document picked on an SD card or a cloud provider write elsewhere; the check says "fine" or "full" about the wrong volume. Fix: for `Where.PICTURES` check the same data partition (usually the same, so correct), for `Where.DOCUMENT` skip the pre-check and rely on the failure path, whose message already says so.
